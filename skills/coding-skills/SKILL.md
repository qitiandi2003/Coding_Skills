# 在现有工程中修改代码

从用户实际遇到的问题写出验收动作。例如“刷新后地图消失”的验收是加载地图、刷新、再次看到同一张地图。说法有多种解释时，先用代码、测试和项目惯例判断。可逆、影响可控的选择按合理假设推进，交付时说明采用了什么假设及其影响。只有在不同解释会显著影响需求、兼容性、数据或设备行为，且现有证据无法判断时，才就那个决定提问。

动手前看工作区差异，找到用户触发的入口、负责该状态的代码和消费结果的下游。沿这条路径确定最小修改范围。复用现有类型、接口和错误处理机制。C/C++ 修改沿用包内的对象所有权、线程模型和构建方式。保留用户已有改动，只清理本次修改产生的废弃代码。

复现时保存输入、旧行为和预期差异。先在最窄的可重复入口验证修复，再走一遍用户实际调用路径。修改共享接口时，挑一个依赖旧行为的调用方做回归。例如给地图改名后，重新打开已有巡检路线，确认仍能按原标识找到地图。

长任务持续跟进，逐项验证用户要求后再交付。等待构建、测试或部署时，跟进结果，诊断并处理授权范围内可恢复的失败，再验证修复。需要额外权限或输入时，先完成能独立推进的部分，再说明具体卡点。若用户同时要求上线，检查运行端实际加载的版本。若要求推送，核对目标仓库、分支和远端提交。

把最终回复写成用户第一次看到的交付说明。先说用户实际能看到什么变化，再说明如何验证、观察到了什么，以及哪些步骤仍待完成。用项目中的通用名称解释关键技术细节，必要的术语首次出现时简要解释。把排查时的临时缩写换成完整含义，让用户只看最终回复就能理解结果。
